# StageCue — Implementation Plan

StageCue is a real-time presentation timer and remote messaging application. It has a **desktop Display** (the laptop that drives the TV over HDMI) and a **mobile Controller** (the operator's phone). It is built as a Laravel modular monolith with a Vue 3 + TypeScript PWA front end, and it is hosted on **Laravel Cloud**.

> **Founding principle:** the desktop presentation must always stay reliable, even when everything else disconnects. The phone is a remote control. The backend is a relay. Neither one is needed for a presentation that is already running.

## Binding decisions (summary)

These decisions are fixed. An implementation agent must not change them without a recorded decision update in this file.

| ID | Decision |
|---|---|
| D1 | **One Laravel app** (modular monolith) serves the API, the broadcasting auth and the SPA shell. There are no microservices. |
| D2 | **Vue 3 SPA + TypeScript** (no Inertia). It uses client-side routing so that the app shell works offline from the service worker. |
| D3 | **Pure, framework-free core** (`resources/js/core/`): the timer engine, message engine and presentation reducer are pure TypeScript functions with an injected clock. Vue, Laravel and WebSockets are adapters around this core. |
| D4 | **The Display is authoritative.** Controllers send *intent commands* (e.g. `TIMER_PAUSE`) and never send full state. The Display validates each command, applies it, persists the result and publishes a snapshot. |
| D5 | **Commands go through HTTP, state comes back over WebSocket.** Controller → `POST /api/sessions/{id}/commands` → Laravel validates, authorises, rate-limits and de-duplicates the command → `ShouldBroadcastNow` sends it to the Display's private channel. The Display sends its ack and snapshot with `POST .../snapshots`, which is broadcast to the controllers' channel. |
| D6 | **Heartbeats use Reverb client events (whispers)** on a presence channel: every 3 s, disconnected after 9 s. Spike task T0.3 must confirm that Laravel Cloud WebSockets accepts client events. If it does not, use the HTTP heartbeat fallback defined in the LLD (§6.4). |
| D7 | **Timer truth is an absolute end timestamp**, plus a monotonic-clock anchor within a session. It is never a decrementing counter. Wall-clock / monotonic reconciliation follows LLD §5.2. |
| D8 | **Display mode (blackout) is orthogonal** to the timer and message state. Render priority: `blackout` > `message` > `timer`. |
| D9 | **IndexedDB is the durable store** (via `idb`). It is written through on every applied command and on every engine transition. It is not written on every tick. |
| D10 | **Every command has an idempotency key.** Each command carries a UUIDv7 `commandId` (de-duplicated on both server and Display), a server-assigned `seq`, and a `baseRevision`. Commands written while offline are saved as **pending drafts** and never replayed automatically. |
| D11 | **Pairing:** a one-time 6-character code or a QR token (10-minute expiry) is exchanged for a Sanctum token for the `Device`. The MVP allows **one active controller per session**. A new pairing replaces the old one, and the Display can revoke it. |
| D12 | **Hosting:** Laravel Cloud app, Laravel Cloud managed WebSockets (Reverb), and Laravel Serverless Postgres. The app uses the free `*.laravel.cloud` hostname, which comes with automatic TLS. |
| D13 | **Local controls on the Display:** keyboard shortcuts (`B` blackout toggle, `F` fullscreen, `Space` start/pause, `Esc` exits fullscreen and shows the setup panel). These satisfy the addendum's "explicitly implemented local control". |
| D14 | **Single display tab:** the Web Locks API (`stagecue-display-<sessionId>`) makes sure that only one tab per browser is the authoritative Display. |

## Ambiguity log (resolved interpretations)

| # | Ambiguity in brief | Decision |
|---|---|---|
| A1 | "Stop" vs "Reset" | **Pause** works while counting down and in overtime. **Reset** returns to `ready` with the configured duration. **Clear Timer** returns to `idle` (stand-by screen). There is no separate `stopped` status. |
| A2 | Timer expiry while a message is visible | The message completes its own lifecycle (timed messages expire, persistent messages stay until dismissed). The compact corner timer switches to overtime styling right away (red pill, `+00:00:05`). The full red TIME UP screen appears when the message ends. Setting `overtimeInterruptsMessage` (default `false`) dismisses the message at expiry instead. |
| A3 | Start Timer when nothing is displayed | `TIMER_START` is valid only from `ready`. The Controller offers a "Display & Start" button, which sends `TIMER_SET` and then `TIMER_START`. |
| A4 | Changing the timer while one is running | `TIMER_SET` is accepted in any status, but the Controller asks for confirmation when the timer is `running`, `paused` or `overtime`. It is a "destructive" command (see A6). |
| A5 | Which clock the Controller shows | The Controller never uses the Display's wall clock. It anchors the snapshot's `computed.remainingMs` to its own `performance.now()` at receipt. The Display re-publishes a snapshot on every change and every 30 s. |
| A6 | "Stale commands" | A command is rejected as `STALE` if it is more than 10 s old by server time when it arrives. Destructive commands (`TIMER_SET`, `TIMER_RESET`, `TIMER_CLEAR`) are rejected as `STALE_VIEW` if `baseRevision` < the Display's current revision. The Controller then refreshes and asks the operator to confirm again. |
| A7 | Display opened while offline | The Display runs in **local-only mode** with keyboard controls. When the network returns, it creates or resumes its session and pairing becomes available. |
| A8 | Number of controllers | One active controller in the MVP. More controllers are post-MVP. |
| A9 | Fullscreen after a reload | Browsers require a user gesture to enter fullscreen. After a reload the Display renders the presentation in the full viewport immediately and shows a 4 s hint, "Press F for fullscreen", in a corner. This is a documented limitation. |
| A10 | Local Wi-Fi fallback (§6.5) | Investigated only (see HLD §15, R6). It is **not** built in the MVP. Browsers cannot open a listening socket, and WebRTC still needs signalling. This is noted as post-MVP. |
| A11 | Custom domain later | The PWA origin will change. Installed PWAs and IndexedDB are bound to their origin. The migration procedure is in 06-Deployment §9. |
| A12 | LLD §5.2 commits a rebase with event `ClockAdjusted`, but the `DomainEvent` union in §3.1 does not list it | `ClockAdjusted` is added to the `DomainEvent` union (and the zod enum). It is only produced by the Display runtime's clock reconciler, never by the reducer. |
| A13 | `PRESENTATION_NEW` gives "revision 0", but every `changed:true` result increments the revision | `PRESENTATION_NEW` is the one exception: the new epoch starts at revision 0. Controllers accept it because the `presentationId` differs (LLD §6.6 rule 2). |
| A14 | T0.3 (Laravel Cloud spike) needs the project's Cloud account | Deferred to the account owner. `STAGECUE_HEARTBEAT_MODE=whisper` stays the default, and the HTTP fallback (T5.11) is built behind the flag so the switch is configuration only. |
| A15 | LLD §5.2 detects a suspension with `dMono > 2000 and dWall > dMono + 1000`, but UNIT CLK-03 suspends with **mono +0**, which that test would classify as a clock change | A forward wall jump is treated as a suspension when the sample is not a regular tick: `dMono > 2000` (missed ticks) **or** `dMono < 500` (a wake-up sample from `visibilitychange`/`pageshow` where monotonic time did not advance). Regular ticks (`dMono ≈ 1000`) with a wall jump stay a clock change. Rule 5's limitation still applies. |
| A16 | T3.5's dev panel must be "removed or hidden in production", but the E2E suite runs against the production build and the keyboard map has no "set timer" key | The panel is rendered only with `?dev=1` (any build). It is not linked anywhere, has no network effect and its buttons never take focus. It also exposes `window.__stagecue` for E2E diagnostics. |
| A17 | BE-06 "20 failed attempts on a session → code rotated", but a wrong 6-character code cannot be attributed to a session | Each failed code attempt increments `pairing_failed_attempts` on every session with a live code. A session that reaches 20 has its code and token cleared, so the guessed space shrinks under attack. The Display notices `pairing: null` on its periodic `GET /sessions/{sid}` and regenerates (T6.6). The per-IP limits (5/min, 20/h) remain the primary defence. |
| A18 | LLD §7.7 keeps a command row "relayed=false" when the broadcast fails, but `status` has no such value | A new status `pending` is used: the row is inserted as `pending` and becomes `relayed` once the broadcast succeeds. A retry of a `pending` or `relayed` command re-broadcasts it. |
| A19 | `GET /sessions/{sid}` returns `pairing` for the display, but the plain pairing token is stored only as a hash | The response carries `{code, expiresAt}` only. The QR URL is available just once, in the `POST /sessions` / `regenerate` response, and the Display keeps it in memory. |
| A20 | LLD §4.9 stores the device credentials under the single key `device['self']` | The `device` store is keyed by role (`display` / `controller`), so one browser can run a Display and a Controller (e.g. two tabs while testing) without one overwriting the other's credentials. |
| A21 | LLD §2 expires controller tokens after 7 days, display tokens after 30, and ends sessions after 7 idle days. The product owner requires that **pairing persists until someone unpairs on purpose** (never broken by network loss or closing the apps) | Both tokens last 90 days and slide on every authenticated request (renewed when < 14 days remain). A session is ended only after 90 days without any activity, and deleted 30 days after it ends. Unpairing stays explicit: the Display's "Unpair this phone", the phone's "Unpair this phone", or pairing another phone. |
| A22 | When the live channel (Reverb) is down, D5 gives the Controller no way to see state or notice an unpair until a reload | Both apps fall back to HTTP every 5 s while the socket is not connected: the Controller polls `GET /state` (last-known mirror; 401/403/410 → unpaired) and the Display polls `GET /sessions/{sid}` (paired controller, pairing code). Commands still need the live channel (D5), so the Controller's buttons stay paused and say why. |
| A23 | Product owner request (after the MVP spec): the stage can show the **time of day** when no timer is set | Contract extension, additive: `display.clock` (default `false`, so older saved states still load) and commands `CLOCK_ON` / `CLOCK_OFF` (empty payload, events `ClockShown` / `ClockHidden`). View priority: blackout > message (+ compact timer, or compact clock if no timer) > timer/overtime > clock > standby. Format `hh:mm:ss AM/PM` in the Display's local time zone (seconds show the clock is live). Display key `C` toggles it; the phone has a "Show the time" switch. A new presentation keeps the preference. |
| A24 | Product owner request (after the MVP spec): an email/password login before the Display or Controller can be used, and **a phone can only pair with a Display logged in to the same account**. This pulls a minimal form of post-MVP item P-03 forward | `users.email` (unique, stored lower-case) and password (≥ 8, hashed). No email verification yet. `presentation_sessions.user_id` = the account that opened the Display. New endpoints `POST /auth/register` (`STAGECUE_REGISTRATION=closed` turns the endpoint off), and a Sign up page that is **hidden by default** (`STAGECUE_SIGNUP_PAGE=shown` brings it back; while hidden, `/signup`, `/register` and `/login?mode=register` go to plain Log in), `POST /auth/login`, `GET /auth/me`, `POST /auth/logout`. Account tokens are Sanctum tokens with ability `account`, 90 days, sliding — a device stays logged in until it logs out. `POST /sessions` and `POST /pairings` now need an account bearer token; pairing a different account → `403 ACCOUNT_MISMATCH` and the code stays valid. Session payloads gain `accountId`; a Display whose stored session belongs to another account (or predates accounts) opens a new one and keeps its local state. Device tokens, the relay and the running presentation are unchanged: a running Display never needs the account again. Logging out on a device is a deliberate unpair (the phone leaves; a Display ends its session). No password reset yet (it needs outgoing email). |
| A25 | Product owner requests: a Display key that sets a near-zero timer, and no zooming on phones | **Tab** on the Display sends a local `TIMER_SET { durationMs: 1000 }` from any timer state (it replaces the clock on the stage; it does not start the timer; Shift+Tab does nothing; Tab no longer moves focus on the Display). Phones: viewport `maximum-scale=1, user-scalable=no`, `touch-action: manipulation` (no double-tap zoom, no tap delay), and iOS `gesturestart` is cancelled (no pinch zoom). |
| A26 | Product owner request: **C shows the time over anything** — a countdown, TIME UP, a reset timer or the black screen — and C again returns to exactly what was there | Supersedes A23's "clock only when no timer is set". `display.clock` becomes a cover like blackout, above it: view priority **clock > blackout > message > timer/overtime > standby**. Exception kept from A23: a message shown while the clock is on appears with the time in its corner (not under a black screen). The timer keeps running underneath (absolute timestamps). The phone's "Show the time" switch is the same flag. Tab (A25) also sends `CLOCK_OFF` so 00:01 is visible. No contract change: same flag and commands, new view rule. |
| A27 | Product owner request: set the timer **from the Display** when the phone can't connect (internet down). Messages stay phone-only | The setup panel (outside fullscreen, FR-D2) gets a Timer card: the phone's H/M/S picker and presets, plus Set, Set & start, Start/Pause/Resume, Reset and Clear. Each is a local command (`DisplayRuntime.local`, like the keyboard, D13), so it needs no network; the phone's mirror catches up from the next snapshot. |
| A28 | Product owner request: **several phones paired with one Display**, so the event doesn't depend on one person. Supersedes D11's "a new pairing replaces the old controller" | Pairing no longer revokes other phones; at most `STAGECUE_MAX_CONTROLLERS` (default 5) per session, else `409 CONTROLLER_LIMIT` (checked before the code is used up). `GET /sessions/{sid}` adds `controllers: [{ id, name, pairedAt, lastSeenAt }]` (oldest first); `controller` stays (the latest phone) for older clients. New `DELETE /sessions/{sid}/controllers/{deviceId}` unpairs one phone (idempotent); `DELETE /sessions/{sid}/controller` still unpairs all. The Display always offers a fresh code and QR (it regenerates after each pairing and on expiry), lists every phone with online status from presence, and has Unpair per phone plus Unpair all (2+ phones). "Controller connected" = at least one phone online. Any phone may send commands; acks and state already go to every phone on the shared controllers channel; simultaneous destructive commands are caught by STALE_VIEW (T8.2). A phone that re-pairs leaves its old pairing itself. Reason `replaced` is no longer sent. |
