# 06 — Deployment & Release Plan (Laravel Cloud, no custom domain)

> Items marked **⚠ verify** depend on Laravel Cloud product details that can change. Task T0.3 / T9.1 confirm them against the live dashboard before they are relied on.

## 1. Environments

| Env | Where | Git branch | Hostname | Purpose |
|---|---|---|---|---|
| **local** | Developer machine (Laravel Herd or Sail) | any | `https://stagecue.test` (Herd TLS) | Development. `composer run dev` runs PHP, Vite, Reverb and the scheduler together |
| **staging** | Laravel Cloud environment `staging` | `develop` | `stagecue-staging-<hash>.laravel.cloud` (assigned) | Integration, phone testing, release candidates |
| **production** | Laravel Cloud environment `production` | `main` | `stagecue-main-<hash>.laravel.cloud` (assigned) | Live events |

No custom domain: the free `*.laravel.cloud` hostname has a managed TLS certificate, which meets the HTTPS requirement for PWA install, service workers, the camera (QR scan), wake lock and fullscreen. **Treat the production hostname as permanent.** Changing it later changes the PWA origin (§9).

### Local phone testing
Phones need a **secure context** for the service worker and the camera, so plain `http://192.168.x.x` does not work. Options, in order of preference:
1. Push to `develop` and test on staging.
2. `herd share` or Expose / Cloudflare Tunnel to get a temporary HTTPS URL to the local app. Reverb must be tunnelled too, or point local `REVERB_*` at the staging WebSocket cluster.

## 2. Laravel Cloud resources (per environment)

| Resource | Production | Staging | Notes |
|---|---|---|---|
| App compute (web) | Flex/Pro, 1 replica, **hibernation OFF** | Smallest size, hibernation ON | No cold start during events (R8) |

| Queue workers | None (MVP uses `ShouldBroadcastNow`) | None | Add one if mail or exports are introduced later |

| Cache | `database` store (rate limiters) | same | Upgrade to Laravel KV (Valkey) if the rate-limiter load grows |
| Object storage | none | none | |

## 3. Build & deploy configuration (Cloud → Environment → Deployments)

**Build commands**
```bash
composer install --no-dev --prefer-dist --optimize-autoloader --no-interaction
npm ci
npm run build              # vite build: SPA + service worker + manifest into public/build
php artisan optimize       # config, route, view and event caches
```
**Deploy commands** (run on each release before traffic switches)
```bash
php artisan migrate --force
```
Runtime: PHP 8.4, Node 22 LTS (build only).

| `STAGECUE_PAIRING_TTL_SECONDS` | `600` | |
| `STAGECUE_COMMAND_STALE_MS` | `10000` | Sent to the clients in the bootstrap config |
| `STAGECUE_HEARTBEAT_MODE` | `whisper` \| `http` | Depends on the T0.3 result |

**The front end gets its real-time config at runtime, not at build time.** `app.blade.php` renders `<script id="stagecue-config" type="application/json">{ reverb: {key, host, port, scheme}, heartbeatMode, staleMs }</script>` from the server config. The API also returns the same block in `/sessions` and `/pairings` responses, and the client persists it in IndexedDB `meta` for offline boots. This means the **same build works on every environment**, and no `VITE_REVERB_*` variables are needed.

## 5. HTTPS & security headers
- TLS terminates at Laravel Cloud's edge. The middleware `TrustProxies` is set to `*` (Cloud's proxy). `URL::forceScheme('https')` outside local.
- Headers, set by middleware on web responses: `Strict-Transport-Security: max-age=31536000`, `X-Content-Type-Options: nosniff`, `Referrer-Policy: no-referrer` (protects the pairing fragment URL), `Permissions-Policy: camera=(self), fullscreen=(self), screen-wake-lock=(self), window-management=(self)`, and a CSP allowing `self` plus `wss://<REVERB_HOST>`.
- `/sw.js`: `Cache-Control: no-cache`, `Service-Worker-Allowed: /`.
- `/build/*` assets: immutable, cached for 1 year (hashed filenames).

## 6. PWA hosting notes
- The SW and manifest are served from the same origin under scope `/`.
- Every deploy produces a new precache manifest. Clients detect the update and apply it only when it is safe (LLD §4.10).
- Never delete old hashed assets in the middle of an event. Cloud deploys replace the whole build, so the SW precache already holds the old assets for clients that are running.

## 7. Logging & monitoring
| What | How |
|---|---|
| App logs | Cloud log viewer (`stderr`). Structured context: `session_id`, `device_id`, `command_id`, `seq`. Message text is never logged |
| Exceptions & performance | **Laravel Nightwatch** (first-party, integrates with Cloud), or Sentry |
| Latency metric | `RelayService` logs `relay_ms` (request → broadcast). The Display reports `apply_latency_ms = applyWall - relayedAt (server-clock corrected)` in snapshots, sampled 1 in 10 and logged |
| Uptime | An external monitor (e.g. Better Stack / UptimeRobot free tier) on `GET /api/time` and the WebSocket host |
| Client errors | `POST /api/client-errors` (post-MVP). In the MVP, the Display keeps the last 200 errors in IDB `meta`, viewable in the SetupPanel → Diagnostics |

## 8. Backups & data
- The data is ephemeral (sessions, last snapshot, the 7-day command log). The presentation itself lives on the laptop.
- Use Serverless Postgres point-in-time restore / branching for production (⚠ verify the retention window on your plan). No extra backup job is needed for the MVP.
- Migrations must be backward-compatible for one release (expand → migrate → contract) so that a rollback is safe.

## 9. Future custom-domain migration (Ambiguity A11)
Origins are `scheme + host`. IndexedDB, the SW and PWA installs are all bound to the origin. When a domain is added:
1. Attach the domain in Cloud and keep the `*.laravel.cloud` hostname serving too (do not redirect immediately).
2. Ship a release where the old origin shows a SetupPanel banner, "StageCue has moved — open <new URL> and install again". Sessions are cheap to recreate, so no state is transferred.
3. After about 30 days, redirect the old hostname with a 301 (navigations only, not `/sw.js`). Then ship a final SW on the old origin that calls `self.registration.unregister()`.

## 10. CI/CD
GitHub Actions on every PR and push:
1. `composer install` → `vendor/bin/pint --test` → `vendor/bin/pest --coverage --min=80` (Postgres service container).
2. `npm ci` → `npm run lint` (eslint + vue-tsc) → `npm run test` (Vitest with coverage gates) → `npm run build`.
3. Playwright (Chromium) against `php artisan serve` + `reverb:start` + the built assets.
4. Nightly: Playwright on WebKit + Firefox.

Laravel Cloud push-to-deploy: `develop` → staging, `main` → production. **Enable "deploy only when GitHub checks pass"**, or protect `main` so it requires green CI and a PR.

## 11. Release procedure
1. Merge features into `develop` → auto-deploy to staging.
2. Run the release checklist on staging: the E2E smoke test (E2E-01, 04, 09, 11, 13), the PWA tests, and the RW tests on real hardware for any rendering or engine changes.
3. Tag `vX.Y.Z` on `develop`, then open a PR `develop → main`. Merging deploys production.
4. Post-deploy smoke test on production (5 min): create a session, pair a phone, start a timer, send a message, blackout/restore, revoke.
5. **Event-day freeze:** do not deploy production within 24 h of a known live event. Running Displays are unaffected by a deploy anyway (their in-memory/IDB state is kept, the SW update is deferred). Relay API compatibility is kept for one version via `v`.

## 12. Rollback
- **App:** redeploy the previous successful deployment from the Cloud deployments list (⚠ verify the one-click rollback). Otherwise revert the merge commit on `main` and push.
- **Database:** migrations are backward-compatible (§8), so a code rollback needs no DB rollback. If a destructive migration is unavoidable, it ships in its own release after the code no longer depends on the old schema.
- **Clients:** a rolled-back build produces a new SW hash, and clients update when it is safe. The contract version `v:1` is kept stable. A breaking contract change requires `v:2` with the server accepting both for one release.
